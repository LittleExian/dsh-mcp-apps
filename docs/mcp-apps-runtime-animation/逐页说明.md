# MCP Apps 运行过程动画：逐页说明

这份文档配合 [15 页运行过程动画](index.html) 使用。动画负责展示数据和控制如何流动，本文档补充每一页的讲解目标、阅读顺序、组件职责、关键结论和可直接使用的讲解词。

## 阅读约定

| 画面元素 | 含义 |
| --- | --- |
| 橙色路径 | 模型发起的入口工具调用 |
| 蓝色路径 | MCP App 发起的交互回调 |
| 绿色元素 | 已建立的宿主能力或通过的安全检查 |
| `callToken` | 一次已保留工具结果的短期能力标识 |
| `sessionId` | 一次已打开 App 视图的短期会话标识 |
| Host | DSH 插件提供的 MCP Apps 宿主运行时 |

动画中的英文方法名、字段名和类名是实际协议或代码标识。例如 `tools/call`、`apps/open`、`AppBridge` 和 `structuredContent` 不做中文改写。

## 第 01 页：全局架构

[打开本页](pages/01-system-map.html)

**讲解目标**

先建立完整心智模型：DSH、插件 Host、MCP Server、AppBridge 和 MCP App 分别位于哪里，以及模型调用和 App 回调为什么是两条不同路径。

**画面阅读顺序**

1. 从左向右看五个节点：DSH 模型 → MCP Apps Host → MCP Server → AppBridge → MCP App。
2. 橙色线表示模型选择入口工具后产生的调用。
3. 蓝色线表示用户在卡片中操作后，App 经 Host 回调原 MCP Server。

**组件职责**

- DSH 模型决定是否调用对 `model` 可见的入口工具。
- MCP Server 提供工具、结构化数据和 HTML App 资源。
- Host 保存原调用关系、创建短期会话并执行权限校验。
- AppBridge 在可信父页面和沙箱 App 之间传递 MCP Apps 协议消息。

**关键结论**

MCP App 不直接选择或连接任意 MCP Server。它提交工具名和参数，Host 根据已保存的原调用关系决定请求可以到达哪个 Server。

> 建议讲解词：整套系统有两条路。第一条由模型发起，用来获得初始数据和 UI；第二条由卡片中的 App 发起，用来响应用户操作。两条路都经过 Host，因此服务绑定和权限边界始终由宿主控制。

## 第 02 页：DSH 启动与插件加载

[打开本页](pages/02-dsh-runtime.html)

**讲解目标**

说明 MCP App 出现之前，DSH 启动阶段已经完成了哪些准备工作。

**实际过程**

1. `dsh web` 读取并组合 `web` profile。
2. DSH 加载 `@exian/dsh-mcp-apps`，调用插件的 `apply(ctx)`。
3. 插件创建 MCP 连接管理器、AppHost 和 Connection RPC。
4. 插件按照配置启动或连接 GitHub Trending MCP Server。
5. 双方完成 MCP `initialize` 和 `tools/list`。
6. 插件把允许模型调用的工具注册到 DSH 工具面。

**组件职责**

- DSH/Cordis 管理插件生命周期和依赖注入。
- 插件管理 stdio 或 Streamable HTTP 连接。
- MCP Server 声明工具可见性和 UI resource URI。

**关键结论**

Host 并不是模型调用后才临时出现。DSH 启动时，它已经连接 Server、读取工具能力并准备好后续的 UI 会话。

> 建议讲解词：在用户发送提示词之前，插件已经完成 MCP 握手并把入口工具注册给 DSH。模型看到的是经过插件筛选后的工具面，不需要理解 iframe 或 AppBridge。

## 第 03 页：模型调用入口工具

[打开本页](pages/03-model-entry.html)

**讲解目标**

解释模型为什么会选择 `show-trending`，以及入口工具返回的数据如何同时服务于模型和界面。

**实际过程**

用户提出“显示本周 GitHub Trending”后，模型调用公开工具名 `wise_mcp__github-trending__show-trending`，参数为 `period=week`、`language=all`。插件将其还原为对应 Server 的 `show-trending` 并执行 MCP `tools/call`。

工具定义通过 `_meta.ui.resourceUri` 声明 `ui://github-trending/app.html`，并通过 `visibility: ['model']` 表示它可以被模型选择。调用结果包含文本 `content` 和适合 App 渲染的 `structuredContent`。

**关键结论**

普通 MCP 工具不会自动变成 MCP App。入口工具必须声明 UI resource，并返回界面能够消费的结构化数据。

> 建议讲解词：模型只完成一次入口调用。它拿到可以回答用户的文本和结构化结果，而工具定义中的 resource URI 告诉 Host：这次结果还有一个可打开的交互界面。

## 第 04 页：保留结果并签发 callToken

[打开本页](pages/04-retain-result.html)

**讲解目标**

说明为什么同一次工具结果需要分成模型出口和 App 出口。

**实际过程**

- 返回给模型的结果保留 `content` 和 `structuredContent`，并移除不应进入模型上下文的 UI 专用元数据。
- Host 在内存中保留原始结果、原始工具输入、Server 身份、工具身份和 resource URI。
- Host 为这条保留记录签发短期 `callToken`，并把它放入 DSH 工具卡片的 presentation metadata。

**组件职责**

`callToken` 不是用户身份，也不是长期凭证。它只表示“Host 中仍然存在一条与当前工具块对应的保留结果”。过期、重启或相关 Server 断开后，这个能力会失效。

**关键结论**

模型和浏览器卡片不需要共享完整的原始返回包。Host 用短期能力标识把两种消费方式安全地连接起来。

> 建议讲解词：这里不是复制两份业务数据，而是把同一次结果分成两个受控出口。模型拿安全结果，卡片拿一个只能恢复原调用的 callToken。

## 第 05 页：打开工具卡片和 App 会话

[打开本页](pages/05-open-app.html)

**讲解目标**

解释聊天中的工具卡片如何从 `callToken` 恢复真正可运行的 MCP App。

**实际过程**

1. DSH 工具视图从工具块 metadata 读取 `callToken`。
2. 可信父页面调用插件 Connection RPC：`apps/open({ callToken })`。
3. AppHost 找回原工具、原 Server、输入、结果和 resource URI。
4. Host 对原 Server 执行 `resources/read`，读取 `text/html;profile=mcp-app` 资源。
5. Host 为这次打开的视图创建独立 `sessionId`。
6. 父页面收到 HTML、原输入、原结果和 `sessionId`，开始创建沙箱。

**关键结论**

每次打开都会创建新的 `sessionId`。多个浏览器视图、React 重复挂载或迟到响应不会共用同一个 App 会话。

> 建议讲解词：callToken 用来找到原调用，sessionId 用来管理当前打开的视图。前者回答“从哪里来”，后者回答“这一次卡片会话是谁”。

## 第 06 页：双层 iframe 沙箱

[打开本页](pages/06-double-sandbox.html)

**讲解目标**

说明 MCP Server 返回的 HTML 为什么不能直接挂载到 DSH 页面，以及双层沙箱分别解决什么问题。

**结构说明**

- 外层 iframe 只运行插件生成的代理脚本，负责 nonce、消息来源、目标窗口和导航状态检查。
- 内层 iframe 运行 MCP Server 返回的 HTML App。
- Host 在执行前为资源包裹 CSP 策略，但不会假设或宣称已经重写、净化所有 HTML。
- 两层均使用 `sandbox="allow-scripts"`，不包含 `allow-same-origin`，因此内层获得 opaque origin。

**安全边界**

内层 App 不能直接读取 DSH DOM、Cookie、Local Storage 或父页面闭包中的 `sessionId`。当 iframe 导航、页面关闭或会话被撤销时，父页面停止接受后续消息。

**关键结论**

双层 iframe 负责隔离不可信代码和可信宿主状态。它不替代 Host 端权限校验，两者必须同时存在。

> 建议讲解词：内层负责“运行 App”，外层负责“守住门”。即使 App 能执行 JavaScript，也只处在一个没有同源权限的隔离环境中。

## 第 07 页：AppBridge 初始化

[打开本页](pages/07-appbridge.html)

**讲解目标**

区分浏览器隔离机制和 MCP Apps 通信协议。

**实际过程**

可信父页面使用 `AppBridge` 创建 Host 端桥接器，并通过 `PostMessageTransport` 绑定内层 iframe。内层 App 使用 MCP Apps SDK 执行 `App.connect()`。随后双方依次交换：

1. `initialize`
2. `initialized`
3. 初始工具输入 `sendToolInput`
4. 初始工具结果 `sendToolResult`
5. 界面尺寸变化 `sizeChanged`

**组件职责**

- iframe 和 CSP 负责隔离。
- `postMessage` 提供浏览器消息通道。
- AppBridge 定义消息结构、生命周期和工具回调协议。

**关键结论**

只建立 iframe 并不等于支持 MCP Apps。Host 和 App 必须实现 AppBridge 约定，才能正确传递输入、结果、尺寸和工具调用。

> 建议讲解词：沙箱解决“能不能信任这段代码”，AppBridge 解决“双方怎样用标准协议交谈”。这是两个不同层次的问题。

## 第 08 页：用户在 App 中交互

[打开本页](pages/08-app-interaction.html)

**讲解目标**

展示卡片打开后，用户操作如何触发第二条蓝色回调路径。

**实际过程**

用户在 GitHub Trending 卡片中点击 Today。App 把界面动作转换为：

```ts
callServerTool({
  name: 'refresh-trending',
  arguments: { period: 'day' },
})
```

这次操作由 AppBridge 发送给可信父页面。父页面不会让 App 传入 Server URL，也不会把 `sessionId` 暴露给内层 App。

**关键结论**

模型没有重新规划，也没有再次选择工具。这是用户直接驱动的 App 交互。

> 建议讲解词：第一次调用是模型决定的，点击 Today 是用户决定的。App 只提交工具名和业务参数，服务选择权仍在 Host。

## 第 09 页：Host 校验 App 请求

[打开本页](pages/09-host-validation.html)

**讲解目标**

说明 AppBridge 请求到达父页面后，为什么不能直接透传给 MCP Server。

**六项校验**

1. **会话**：`sessionId` 存在且仍然有效。
2. **服务器**：目标工具属于原调用绑定的同一个 MCP Server。
3. **可见性**：工具 metadata 包含 `visibility: ['app']`。
4. **资源**：若目标工具声明 resource URI，它必须与入口工具一致。
5. **数据边界**：工具名、参数、结果与 HTML 大小符合限制。
6. **运行限额**：请求未超过并发、频率和超时限制。

要求独立 task 执行的工具也不会被当作普通 App 回调执行。

**关键结论**

AppBridge 提供标准消息，但授权决定由 Host 完成。App 的请求只有通过全部检查后才能进入 Server。

> 建议讲解词：App-visible 不代表无条件可调用。它只是第一层声明，Host 还要检查这次会话是否有权调用这个 Server 的这个工具。

## 第 10 页：原 MCP Server 执行业务

[打开本页](pages/10-server-response.html)

**讲解目标**

明确插件 Host 和 MCP Server 的业务责任边界。

**实际过程**

1. 内层 App 发出 `refresh-trending`。
2. AppBridge Host 回调可信父页面。
3. 父页面调用 `apps/call({ sessionId, name, arguments })`。
4. AppHost 完成权限校验并解析原 Server。
5. 插件对原 MCP Server 执行标准 `tools/call`。
6. Server 查询数据并返回新的 `CallToolResult`。

**关键结论**

插件不会接管 GitHub Trending 的业务规则。它负责路由、会话和安全；数据查询与结果构造仍由 GitHub Trending MCP Server 完成。

> 建议讲解词：Host 是受控通道，不是业务后端。App 的第二次工具调用最终仍然落到原 MCP Server。

## 第 11 页：只更新 App 状态

[打开本页](pages/11-state-update.html)

**讲解目标**

解释为什么聊天日志仍显示 weekly，而卡片可以已经切换为 Today。

**实际过程**

`refresh-trending` 返回新的 `structuredContent` 后，App 更新自己的视图状态。该请求走的是插件的 `apps/call` Connection RPC，不经过 DSH 模型工具事件流。

因此：

- DSH session 中保留原始 `show-trending(period=week)` 调用和结果。
- MCP App 当前展示 `refresh-trending(period=day)` 的结果。
- App 回调默认不会新增一条模型工具调用日志。

**关键结论**

模型上下文和 App 交互状态彼此关联，但并不等同。这样可以避免每次筛选都消耗一次模型推理。

> 建议讲解词：左边是模型当时做过什么，右边是用户现在在卡片里看到什么。App 可以继续交互，但不会改写已经发生的模型记录。

## 第 12 页：插件与 MCP Server 的职责

[打开本页](pages/12-responsibilities.html)

**讲解目标**

回答接入新的 MCP App 时，哪些能力可以复用，哪些内容需要业务方实现。

**插件 Host 负责**

- stdio 和 Streamable HTTP 连接
- MCP 工具发现与 DSH 工具注册
- `callToken`、`sessionId` 和生命周期
- UI resource 读取
- 双层 iframe 与 CSP
- AppBridge Host
- 工具权限、资源绑定、大小、频率和并发校验

**MCP Server 与 App 负责**

- 对 `model` 可见的入口工具
- 对 `app` 可见的交互工具
- `ui://` HTML 资源
- 业务数据和 `structuredContent`
- App 端 `App.connect()`、渲染和交互逻辑

**关键结论**

新的标准 MCP App 通常只需要实现 Server 和 App，并在 DSH profile 中增加 Server 配置。只要协议和安全要求一致，无需为每个业务 App 修改 DSH 核心或重写宿主。

> 建议讲解词：插件提供可复用的舞台和安全边界，MCP Server 提供具体节目。新增业务时主要替换右侧，不需要重新建一套宿主。

## 第 13 页：WiseWork 模拟 MCP App 链路

[打开本页](pages/13-wisework-chain.html)

**讲解目标**

把此前 WiseWork 中实现的 MCP App 模拟链路映射到同一套 Host 心智模型。

**实际过程**

1. OpenCode 通过 ACP 产生工具 running/completed 事件。
2. `RuntimeMcpAppBroker` 合并工具运行状态并识别带 UI 的结果。
3. `McpAppSessionManager` 在 Electron 主进程维护工具、资源和会话绑定。
4. IPC/Preload 向 Renderer 暴露受控的 open、call、close 能力。
5. Renderer 创建双层 iframe，让 DTS App 运行在 opaque origin 中。
6. AppBridge 传递初始数据，并接收 `callServerTool`。
7. DTS MCP Server 通过 `MockDtsGateway` 完成演示提交。

**与 DSH 插件的对应关系**

| WiseWork | DSH 插件 |
| --- | --- |
| ACP 工具事件 | DSH 模型工具事件 |
| Runtime Broker | DSH 工具视图适配与结果识别 |
| Session Manager | AppHost manager |
| Electron IPC/Preload | DSH Connection RPC |
| Renderer 双层 iframe | DSH 工具卡片双层 iframe |
| DTS MCP Server | GitHub Trending MCP Server |

**关键结论**

两套实现的宿主环境不同，但核心链路一致：从模型工具结果识别 UI，创建受控会话，在沙箱中运行 App，并把 App 工具请求绑定回原 Server。

> 建议讲解词：WiseWork 使用 Electron 主进程和 IPC，DSH 插件使用 Host 与 Connection RPC。承载技术不同，但会话、沙箱、AppBridge 和原服务器绑定的逻辑相同。

## 第 14 页：真实 DSH 录制

[打开本页](pages/14-dsh-recording.html)

**讲解目标**

用真实 DSH 界面验证前 12 页描述的链路确实能够运行。

**录制内容**

1. 在 DSH 输入明确的 GitHub Trending 工具请求。
2. 模型调用 `wise_mcp__github-trending__show-trending`。
3. 插件从工具结果恢复 MCP App 卡片。
4. GitHub Trending UI 在双层沙箱中显示。
5. 点击 Today，通过 AppBridge 调用 `refresh-trending`。
6. 卡片更新，原模型工具记录保持不变。

**观看重点**

关注聊天工具记录与卡片内容的差异。前者证明模型入口调用成功，后者证明 MCP App 后续回调成功。

**关键结论**

该录制同时验证了 DSH 插件加载、MCP Server 调用、UI resource 渲染和 AppBridge 交互四个环节。

> 建议讲解词：这里不再是架构模拟。录制中的 DSH 使用实际插件和 GitHub Trending MCP Server，先由模型打开卡片，再由用户在卡片里完成第二次工具调用。

## 第 15 页：真实 WiseWork DTS 录制

[打开本页](pages/15-wisework-recording.html)

**讲解目标**

用已有 WiseWork 测试录制验证第 13 页的模拟链路。

**录制内容**

1. 用户输入“请打开 DTS 表单”。
2. OpenCode 触发 DTS 入口工具。
3. WiseWork Runtime Broker 和 Session Manager 创建 App 会话。
4. DTS App 在双层 iframe 中打开。
5. 用户填写问题、严重程度、分类和影响等字段。
6. App 通过 AppBridge 调用仅对 App 可见的提交工具。
7. `MockDtsGateway` 返回成功状态和模拟 DTS 编号。

**观看重点**

表单打开来自模型入口调用；填写和提交发生在 App 内。提交阶段无需模型重新规划，因此能直接响应用户界面操作。

**关键结论**

录制证明 WiseWork 的 Host、沙箱、AppBridge 和 App-only 工具调用已经形成完整交互闭环。

> 建议讲解词：最后这段把同样的宿主模式应用到 DTS 场景。模型负责打开应用，用户负责填写和提交，Host 负责把提交安全地送回原 DTS MCP Server。
